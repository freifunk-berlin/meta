#### Alte Firmware

Uptime ist gut, aber aktuelle Firmware (mit geschlossenen Sicherheitslücken) ist besser. Für größere Updates ist folgender Workflow empfehlenswert. Unterstützt gerne beim [🛠 upgraden auf OpenWrt 25.12](https://github.com/freifunk-berlin/bbb-configs/issues/1571)

```bash
check-versions.sh
generate-images.sh -l tmp/update.txt
mass-update.sh
```

#### Low mem/flash

Das `falter-common` package zieht aktuell als Metapaket viele dependencies rein. Das macht Probleme auf alten Geräten. [🛠 Reduce falter-common to minimum](https://github.com/freifunk-berlin/falter-packages/issues/530).

#### Stabilitätsprobleme

OpenWrt 25.12 führt in Einzelfällen auf bestimmter Hardware zu Problemen und kernel panic. Aktuell haben wir keinen Prozesss dokumentiert um gute Reports für OpenWRT zu machen. Als erster Schritt stellen wir [von 25.12-SNAPSHOT auf 25.12.4 um](https://github.com/freifunk-berlin/bbb-configs/pull/1650). Wenn die crashes trotzdem auftreten können die debug symbols damit entschlüsselt werden.

## IPv6 Prefix

### Alter und neuer Prefix

Aktuell nutzt Freifunk Berlin noch einen Prefix einer Firma, aber der Kontakt ist nicht mehr wirklich vorhanden. Wenn irgendwann mal irgendwas sein sollte würde das zu Problemen führen. FreiFunktion e.V. holt sich ein eigenes v6 Prefix. Parallelnutzung von altem und neuen Prefix sorgt **nicht** für Brüche im Netz.

### Prefix Zuordnung

Zur Zeit werden Wahlbezirke für die geografische Zuordnung verwendet. Allerdings sind die Grenzen und Nummern dieser Wahlbezirke sind nicht mehr aktuell und es ist verwirrend. Daher sollte eine bessere Zuordnungsvariante gefunden werden.

- Vorschläge waren: Grid mit Größe X, PLZ, Bezirksgrenzen, VBB-ABC-Ringe + Himmelsrichtung
- Favorit: PLZ
- Die PLZ könnte auch direkt im Prefix abgebildet werden
- Aktuell wird die geografische Zuordnung noch **nicht** für das Routing verwendet
- [🛠 IPv6-Prefix Zuordnung nach PLZ](https://github.com/freifunk-berlin/config.berlin.freifunk.net/issues/109)

### Contributing Guidelines

Was muss eine neue Person machen, damit ihr Commit in den Main-Branch kommt?

    - Soziale Aspekte: Die Person sollte zumindest einer Maintainer-Person bekannt sein und eine gewisse Nähe zum Freifunk ist wünschenswert

    - Schlechte Erfahrungen mit Hacktober-Fest

    - Kleine Fixes wie Rechtschreibfehler in der Readme sind auch von gänzlich Unbekannten annehmbar


Vorschlag für Guidelines

- Aufbau

    - Allgemeiner Teil in die Guidelines. Spezifische Details sind in die entsprechenden Reporitories packen

    - Space vs. Tabs? Ist je nach Dateityp unterschiedlich. Die Kontrolle soll die CI-Pipeline übernehmen

    - Prozesserklärungen:

    - Anlegen und richtiges kategorisieren von Issues

    - "Wie kommt dein Issue/Commit nach Main?"

    - (Fork) > Branch > Commit > Rebase > Approvement > Merge > Delete Branch

    - Einen Maintainerfreundlichen Commit aus einem Fork mergen

- Zielgruppe: Einzelpersonen und Organisationen, die mehr als Falter machen wollen und sich konstruktiv am Berlin-Brandenburger-Freifunk-Netz beteiligen möchten
